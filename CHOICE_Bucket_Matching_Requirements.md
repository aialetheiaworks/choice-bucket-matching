# CHOICE — Root-Word Bucket Matching: Requirements & Design Plan

## 1. Goal

Given the **master prompt** generated by Choice Forge from the user's initial query, extract meaning from it, match that meaning against the **Knowledge Bucket Library**, and surface up to **5 tooltip lines** nudging the user to think about the business dimensions they haven't explicitly covered yet — in the form:

> "If you are speaking about **MARKET**, also consider thinking about → market size, maturity, growth, and dynamics."

This is a semantic matching problem, not a trained classifier — the "Intent Classifier" box in the architecture diagram is really a **matching + ranking pipeline**.

---

## 2. Inputs

- **Master prompt from Choice Forge only** (longer, structured — e.g. "Increase annual sales of premium office chairs by 30%..."). This is the single source text for extraction.
- **2026-08-19 workflow change:** the raw initial user query is no longer a separate input to this pipeline. Choice Forge already consumes the raw query to produce the master prompt, so this pipeline doesn't need it a second time — everything downstream (extraction, matching, scoring) operates on the master prompt alone.

---

## 3. NLP Processing Requirements (spaCy)

- **Model choice**: needs a spaCy model with real word vectors for semantic similarity, not `en_core_web_sm` (no usable vectors) — use `en_core_web_md` or `en_core_web_lg`, or plug in `en_core_web_trf` / transformer-based similarity if quality matters more than  latency.
- **Tokenization + lemmatization**: reduce every word in query + master prompt to its lemma/root (e.g. "pricing," "priced," "prices" → "price").
- **Stopword removal**: filter out non-content words (articles, prepositions, etc.).
- **POS filtering**: keep nouns, proper nouns, verbs, and adjectives; drop the rest — these carry the business meaning.
- **Deduplication**: take the set of unique root words extracted from the master prompt.
- **Multi-word phrase handling**: some bucket concepts are two words ("Value Proposition," "Business Objective," "Customer Experience") — need noun-chunk / phrase extraction, not just single-token roots, so these can match as phrases too.
- **Negation handling (open question)**: "without expanding the sales team" — should this suppress the "Resources/Talent" bucket, or still surface it as a constraint? Needs a decision (see §9).

---

## 4. Bucket Matching Requirements — beyond literal names

This is the biggest gap versus what's in the PDF today: the PDF only gives a **bucket name + one prompt line** per bucket. To match on meaning (not just the literal word "customer"), each bucket needs to be expanded into a **keyword/synonym set**.

Two approaches, not mutually exclusive:

**a) Curated keyword/synonym list per bucket**
Each bucket gets a maintained list of related terms.
Example — `Customer`: customer, client, buyer, user, segment, persona, audience, consumer, purchaser, end-user.

- Pro: precise, explainable, easy to debug/tune.
- Con: manual effort to build and maintain ~60–80 lists; misses novel phrasing.

**b) Semantic similarity via spaCy word/phrase vectors**
Compare each extracted root word/phrase's vector against the bucket name's vector (or the bucket's prompt text vector), using cosine similarity above a threshold.

- Pro: catches synonyms and related concepts without manual lists.
- Con: needs threshold tuning; can produce false positives/negatives; vector quality varies by model.

**Recommended: hybrid.** Use (a) as the primary, high-confidence signal, and (b) as a fallback/boost so bucket coverage doesn't depend entirely on manually maintained lists. This needs to be explicitly decided and documented before implementation.

- **Requirement**: build and store a keyword/synonym set for every bucket in both Tier 1 (~60 buckets) and Tier 2 (~20 buckets) libraries.
- **Requirement**: decide whether matching runs against Tier 1 only, Tier 2 only, or both — and if both, how overlapping bucket names (Value Proposition, Product Strategy, Continuous Improvement appear in both tiers) get deduplicated or merged.

---

## 5. Scoring & Ranking Requirements

Need an explicit, documented rule for "at most 5 buckets" selection:

- **Match scoring**: how is a bucket's relevance score computed? e.g. count of matched root words + phrase matches, weighted by similarity score. (No query-vs-master-prompt weighting needed — see §2, the master prompt is the only input now.)
- **Threshold**: minimum score for a bucket to be considered "matched" at all.
- **Tie-breaking rule**: when more than 5 buckets clear the threshold, what breaks ties? Options: highest cumulative match score; a fixed priority order among buckets (e.g. Customer/Value Proposition/Business Objective always outrank Localization/Accessibility unless strongly matched); frequency of the matched term across both texts.
- **Fewer-than-5 case**: if only 2–3 buckets match, do we pad the tooltip with high-priority "always relevant" buckets (e.g. Business Objective, Risk), or show fewer than 5 lines?
- **Zero-match case**: fallback behavior needs to be defined (generic prompt? most common buckets by default?).

---

## 6. Tooltip Generation Requirements

- **Template**: "If you are speaking about **{BUCKET NAME}**, also consider thinking about → {knowledge prompt}."
- **Max 5 lines**, ordered by rank (highest relevance first, or should Tier-2/strategic buckets always sort above Tier-1/tactical ones?).
- **Formatting**: bucket name emphasis (caps/bold), consistent phrasing across all buckets.
- **Localization (future)**: template needs to support translation if the platform goes multi-language.

---

## 7. Data Persistence Requirements (from the PDF's Knowledge Graph section — still applies here)

Every time a user runs this flow, the following must be saved and versioned:

1. Typed responses by the user (the raw query + any follow-up answers)
2. AI prompts/summary generated (master prompt, tooltip lines shown, any AI-generated summary)
3. Decision tables / knowledge database entries
4. Knowledge Graph — actors (including hidden/phantom actors like regulatory or macro-economic forces) and relationships between them

Additional requirements tied to the matching step specifically:
- Store **which buckets were matched**, their scores, and which root words/phrases triggered each match — needed for debugging, tuning thresholds, and potentially showing the user "why" a bucket was suggested.
- Store the **match history per objective**, since re-running the flow later (or editing the KG) may change which buckets surface.

---

## 8. Technical Architecture Requirements

- **Bucket library storage**: move the bucket library out of a PDF/table into a structured store (DB table or config file — JSON/YAML) with fields: `bucket_name`, `tier` (1 or 2), `prompt_text`, `keyword_synonym_list`, `priority_weight`.
- **Pipeline stages**: ingest text → spaCy NLP (tokenize/lemmatize/POS-filter) → extract unique root words + phrases → match against bucket library (keyword + semantic) → score → rank → select top 5 → render tooltip.
- **Service boundary**: should this be a standalone microservice/function callable from Choice Forge, or embedded logic within the CHOICE product backend?
- **Performance**: matching needs to run at interactive/tooltip speed (sub-second), so semantic similarity computation (if using vectors) needs to be efficient — precompute bucket vectors once, not per request.
- **Knowledge Graph storage**: needs a schema decision — graph database (Neo4j, etc.) vs. relational tables modeling nodes/edges — to support add/remove nodes, edit relationships, and partial/filtered views (e.g. "show only actors who are also stakeholders").

---

## 9. Open Questions / Decisions Needed Before Implementation

- Negation handling: does "without expanding the sales team" suppress or reinforce a bucket? - lets fosus on positive statementes for beginning
- ~~Query vs. master prompt weighting~~ — resolved 2026-08-19: the raw query is no longer a separate pipeline input, so there's nothing to weight against the master prompt.
- Tier 1 vs Tier 2: run both, and if so how do they combine into one 5-line tooltip?
- Exact similarity threshold and scoring formula (needs empirical tuning against real sample queries).
- Priority/tie-break order among buckets when scores are equal.
- Fallback behavior for <5 or 0 matches.
- Who owns/maintains the synonym lists over time as new phrasing patterns are observed?
- Do we need a test/eval set — a set of sample objective statements with expected "correct" bucket matches — to validate and tune the matching logic before shipping?

---

## 10. Suggested Next Steps

1. Decide the open questions in §9.
2. Build the structured bucket library (JSON/DB) with synonym lists for all ~60 Tier 1 + ~20 Tier 2 buckets.
3. Build a small eval set of 15–20 sample objective statements with human-labeled "expected buckets" to test the matching pipeline against.
4. Prototype the spaCy pipeline (extraction → matching → scoring → ranking) against the eval set and tune thresholds.
5. Wire in tooltip rendering + persistence (matched buckets, scores, triggering terms) once matching quality is acceptable.
